# Offline adapter and remaining live boundary

`pocket-monaco-offline-executor.ts` is unmounted. It accepts only a branded, inert-data mock transport and a branded disposable journal in a new temporary directory. It has no provider client, fetch path, credential read, live RPC injection, activation flag or paid execution mode. `syntheticEngineeringFixture:true` is mandatory on its approval fixtures. Those fixtures exercise gates; they are not human decisions. Every return records zero real provider calls. Actual prepared inputs without approvals stop before a claim or mock send.

The adapter reads the existing version 2.3 packet and its exact request inventory. Manifest/request inventory hashes, all six case artifacts, request bytes, image membership, spend fingerprints and pinned scanner dependencies are checked. It reuses `verifyPocketBenchmarkEnvelope`, `recoverPrecisionGeometry` and `calibratePocketAnalysis`; it never imports the live scanner route. The unchanged route hash binds the copied conditional rescue predicate. Main and primary precision are the two base passes; rescue is conditional on the same missing-side/empty-level predicate. Malformed precision does not manufacture a retry. A missing, failed or incomplete response is not a successful analysis.

The offline journal models the existing `claim/submit/record receipt/void/account` RPC lifecycle. Claim reserves all three slots; submit is durably written before transport. Writes use exclusive transaction locks, file/directory fsync, atomic rename and checksums. Scope A and B bindings are immutable after first claim. A retains the aggregate $5 cap and explicit prior exposure; B has its own 44-case allowlist and proposed $14.0624 direct-token ceiling. Historical accounting is untouched. Across both scopes one chart can hold the journal lease. Duplicate cases and repeated slots fail. Reopening the same journal cannot reset the budget or retry a case.

Only unsubmitted slots are voided. Missing identity/usage, transport uncertainty, cancellation after submission and receipt-persistence interruption retain submitted reserves. Receipt recovery verifies exact request hash/fingerprint and immutable identity/usage/raw bytes, makes no send, and never turns an interrupted case into a measured success or authoritative financial settlement. Replaying an old receipt cannot clear a newer chart's lease. As in the existing SQL contract, both base receipts are required for reserved accounting; a cancelled partial base path remains held. Stale locks and corrupt journals fail closed, without automatic repair or lock stealing.

This is an engineering journal, not a deployed database ledger or replacement for SQL security. Its checksum detects corruption; it is not an adversarial signature. Disposable-store creation is permitted solely because no store can reach a real provider. The existing SQL remains unchanged, pinned and six-case bounded. A future live bridge must use that durable authority and its billing-release veto; B needs a separately approved aggregate ledger design, never eight recycled six-case ledgers. No such live bridge, B database change, deployment or permission expansion is enabled here.

The offline profile serializes its internal calls. Production currently starts the two base passes together. Thus mock wall-clock latency demonstrates lifecycle recording only and must not be reported as provider or route latency. Exact requests, pure geometry and the rescue predicate are reused; live orchestration/parity must be explicitly included in a future approved candidate freeze. No synthetic result enters the 50-case report or `RAW-OBSERVATIONS.json`.

Remaining live work is intentionally gated on actual human references/protocol, approved candidate freeze, processor/security review, budget headroom and specific paid-run authority. `APPROVAL-RECORD.json` is the single decision record. It grants nothing. The first-six review ZIPs contain only each reviewer's existing blank worksheets, images and neutral instructions; the weak 4h H&S remains unaccepted. No further data preparation or rescreening is needed before those decisions.
