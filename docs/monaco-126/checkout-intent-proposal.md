# Durable Checkout intent — UNINSTALLED, bound-customer proposal

This isolated successor of PR130 at10451b5 wires the proposed protocol into the candidate Pocket Checkout route. It is not deployed and installs no hosted SQL. It does not enable new customer checkout or prove one active subscription per customer. Its invariant is narrower: **one permanent unresolved intent per verified application UUID, and at most one application dispatch through this protocol**. A known session can be reused; an ambiguous result, expired session or old idempotency key never authorises another creation. No close/reopen RPC exists. Root alone owns monaco-checkout-intent-proposal-126-20261019; all previous candidates remain frozen.

## Helper integration contract

`createPocketCheckoutStripeDriver(stripe)` captures Account retrieval, Price retrieval and Checkout creation from the same server SDK instance. The driver verifies actual `Account.id`, exact `Price.id`, `Price.livemode`, the existing £4.99 monthly price contract and `interval_count === 1`. Missing Account permission or any mismatch yields HOLD; a bare account/mode config object cannot replace this factory-branded driver. Creation overrides SDK defaults with `maxNetworkRetries: 0`, `timeout: 10000` and the durable key.

`ensurePocketCheckoutIntent({scope, parameters}, {authorise, rpc, stripeDriver}, request.signal)` returns `{kind:'READY', intentId, url}` only after the known provider result is durably recorded, or `{kind:'HOLD', reason, intentId?}`. `authorise` must call the existing trusted server identity path; `scope` and the exact offer parameters come from the server catalog and durable UUID/customer binding, never form customer IDs or emails used to discover a customer. Existing signature-verified subscription webhooks and active-subscription admission remain mandatory. Existing origin/CSRF, cancellation and browser session checks remain in the route.

The candidate route now calls this actual helper and factory, rechecks server getUser identity, and has no direct Pocket create fallback. Missing UUID/customer binding, exact40-character build SHA, server-only POCKET_CHECKOUT_STRIPE_ACCOUNT_ID, explicit POCKET_CHECKOUT_STRIPE_MODE=test/live, schema or baseline yields HOLD. These non-secret scope settings are not an enable flag and have not been configured on any host. Actual SDK account/Price observations must agree; no new credentials are requested or created. Unbound first-customer provisioning and resumed/expired/cancelled subscription reconciliation remain unimplemented. Non-Pocket legacy catalog flow is unchanged. Candidate return URLs must be HTTPS. No current paid admission or historical renewal validator is changed.

The helper clones inputs before its first await, verifies the exact stored canonical text/hash/scope/key, and passes only the deep-frozen stored parameters to the SDK driver. The SQL hash is SHA256 of **the exact `jsonb::text` bytes returned to the helper**; it is not compared with `JSON.stringify`. The database appends intent/candidate metadata and a fixed 45-minute expiry once, when the baseline is attested. A dispatch requires at least 30 minutes remaining. Another candidate, price, customer, account/mode, origin or attribution cannot silently alter that intent.

## Failure, expiry and race semantics

Stripe idempotency caches the first executed status/body, including 500, and keys may be pruned once at least 24 hours old. Concurrent conflicts before execution may not be cached. This protocol never treats those conditions as permission to resend; it dispatches once and retains unresolved state. A lost claim response cannot obtain the previous token. A successful provider result followed by a failed persistence response remains HOLD; recovery reuses a known persisted result or requires a separately designed proof-bearing reconciler. There is no time bucket and no automatic release after 24 hours.

The additive subscription trigger uses the same UUID advisory transaction lock as intent preparation/claim. A committed webhook before the claim must block creation. A webhook after a committed claim cannot undo an already permitted remote request: the known result is saved and its redirect withheld if active entitlement is then present. PostgreSQL and Stripe do not share a transaction. Delayed/missing webhooks, other applications, legacy sessions and people using the Dashboard remain outside the proven invariant; this is not global subscription uniqueness.
