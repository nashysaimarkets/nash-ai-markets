# Checkout inventory collector — source evidence only

20 October 2026. Successor of PR131 `2994b2859ef7bcc22b9ee38a5b966e1806e47994`. This adds an unmounted server helper and offline tests. No route, environment variable, baseline issuer, SQL, role, credential, provider request or activation is added. Existing customer admission and prices are unchanged. Root publishes the integrated source checkpoint in issue126.

`createPocketCheckoutInventoryReader(existingStripeInstance)` captures exactly five SDK GET methods: authenticated account retrieval, exact Customer retrieval, subscription listing, Checkout Session listing and subscription-schedule listing. All use the same existing instance, a 5-second request timeout and zero SDK retries. No provider write method is captured or called. Existing pinned SDK/API contracts are preserved.

`collectPocketCheckoutInventory(scope, dependencies, signal)` requires a trusted server identity/binding callback before reads and again after all pages. Scope includes exact UUID, intent, existing customer, account, mode, candidate, price and offer. There is no email-based Customer discovery. Provider Customer and every observed object must match the bound customer/mode; any supplied UUID metadata or Checkout client reference must agree. Missing metadata is allowed for the already accepted durable legacy binding, never as an alternative ownership proof. Deleted customers, unknown states, malformed replies, conflicting identifiers, duplicate objects, a failed read or a changed authority return HOLD with no partial receipt or raw provider error.

Each collection lists all subscription statuses, all Checkout Sessions and all subscription schedules for the customer. It uses only customer/limit/cursor filters; no time or price filter can hide pending obligations. Pagination requires an explicit boolean `has_more`, the expected fixed list path, at most100objects/page and an advancing unique last-ID cursor. More than20pages per collection returns HOLD rather than presenting a truncated inventory as complete. The whole observation is limited to45seconds and rejects clock reversal. Aborts and timeouts ignore late results and start no follow-up read; an in-flight SDK GET may finish under its own request timeout.

Active, trialing, past-due, unpaid, paused and incomplete subscriptions count as blockers. Open Checkout Sessions and active/not-started schedules also count as blockers. A complete subscription Checkout needs a terminal subscription corroborated by the full subscription inventory; terminal schedules with unresolved underlying or released subscriptions require reconciliation. Only canceled/incomplete-expired subscriptions are terminal for these comparisons. **A future not-started schedule must not disappear merely because no subscription exists yet.**

A COMPLETE result means only that these bounded GET inventories completed. Its immutable minimal receipt includes exact scope, timestamps, sorted object IDs/statuses/references, page counts and blocker counts. SHA256 covers the exact canonical receipt text. Names, emails, provider metadata, checkout URLs, tokens and raw responses/errors are omitted. Every receipt explicitly contains `authorisesCheckout:false`; an empty inventory is never a baseline attestation or permission to create a session.

## Remaining acceptance

The collector is not wired into Checkout or an attestation RPC. It does not implement first-customer provisioning, reconciliation/reopening, an authenticated verifier issuer or fence/cutover authority. Lists are separate non-atomic observations, not a Stripe transaction. Complete authenticated read permission, exact exclusive legacy-route/in-flight/recovery-link cutover evidence, fresh binding/price scope, independently governed issuer/receipt handling and specific shared-live approval remain necessary before any proposed baseline can be accepted. Other writers, Dashboard actions, invoices, payment intents, pending asynchronous collection and other provider resources can require additional reconciliation; no global subscription uniqueness is claimed. Required subscription webhooks and the existing commercial/tax review remain unchanged.

No hosted database, Stripe customer/subscription, signed native build, owner subscription or production environment was changed. Genuine provider acceptance is UNTESTED. Rollback removes this unmounted module/tests; it must never reset any existing unresolved Checkout ledger or restore direct Pocket creation.

## Independent pinned-contract correction

Independent acceptance found that Stripe18.5 declares `Checkout.Session.metadata` nullable, as it does schedule metadata. An authenticated, bound expired Session with `metadata:null` incorrectly produced HOLD. The added real-collector test reproduced35PASS/1FAIL on `1677a3e`; accepting null for these two documented object types produces36/36PASS/0skip. Supplied foreign UUID metadata is still rejected; required Customer/Subscription metadata remains non-null under the pinned contract. Session client references/subscription references already accept their documented null values. Null Session status remains HOLD because it cannot establish a terminal or open state; customer/reference expansion is not requested, and unexpected expanded payloads stay HOLD rather than silently changing the reviewed shape. No authority or activation changes.
