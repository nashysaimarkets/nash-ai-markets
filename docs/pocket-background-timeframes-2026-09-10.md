# Automatic preparation of uploaded timeframes

The owner requested that other uploaded charts start analysing after the main result opens, so customers can switch without starting a new scan on each first selection.

The current result starts a bounded queue for every remaining upload. Each request keeps all original screenshots, promotes its selected source to primary, and uses the existing complete analysis and precision pipeline. Up to four reports run independently. A separate single-lane image queue serialises encoding, deterministic measurement and recovery-image creation to bound phone canvas memory. The customer can read the main report throughout preparation.

Selecting a running chart shares its promise. Selecting another chart immediately changes the pending selection and shares any existing work; the latest selection wins. Returning to a ready report does not abort paid work. Late completion is cached without changing the current selection. State updates merge results that completed during a pending selection, and a five-entry queue cache closes the race between completion and a new click. New sessions and evidence corrections invalidate old work and cache entries.

The selector shows waiting, queued, analysing, ready or retry states. Automatic preparation requires an entitled native Apple session, never consumes the free Apple scan or opens a paywall, pauses before starting more work in hidden pages, and respects response allowance and retry headers. Failed charts require a customer retry; background failures do not replace the visible report. Preparing all uploads can use more AI credits than viewing only the main result.

Validation exercises the actual preparation, request and selection handlers with controlled provider responses: all four supporting reports complete without selection; all five views then switch repeatedly without extra scans; simultaneous selection shares a request; switching preserves active and completed reports; failures, entitlement expiry, service allowance, hidden pages, resets and corrections are covered. Rendering checks cover background statuses and all enabled timeframe buttons during a pending selection. The real executor test holds one response while the other three finish, checks peak canvas concurrency of one, checks all five sources on each request, and checks that out-of-order responses do not restore spent allowance or clear a provider pause. TypeScript passes. These are orchestration and regression checks, not new live-provider speed or chart-accuracy measurements.

The native Apple shell is pinned to an immutable Vercel deployment. Publishing the Sites web version does not update an already installed Apple build; the native source and release pin require a separate build.

## Follow-up prompted by the customer recording

The September 10 recording used the correct previous Vercel revision. Runtime logs showed the first five-chart result completed in 51.6 seconds, followed by a timeframe report whose first attempt timed out at 105.1 seconds and whose recovery completed at 145.6 seconds. The single active provider job blocked all remaining uploads. Increasing the waiting animation or relying on a sequential prefetch did not solve this problem.

The scheduling fix removes the shared provider bottleneck while retaining the full image pack, report schema, precision verification, native entitlement and server scan limits. After output begins, report recovery now uses the actual 15-second output-idle budget even before the initial reasoning deadline; the total deadline and one-recovery bound are unchanged.

Browser verification used the real rendered PocketBullseye component and actual encoding/measurement/request/selection path with fictional chart responses. One response was deliberately held: all four requests started, three became ready, and selecting 4H while 30M was pending immediately changed the visible report without another request. The isolated HTTP preview needed a fixture-only cache-key substitute because WebCrypto is unavailable on insecure origins; production WebCrypto was not changed. All fixture source edits were removed before build. This verifies scheduling and switching under a controlled stall, not live AI latency or provider accuracy. The installed Apple binary remains separately pinned.
